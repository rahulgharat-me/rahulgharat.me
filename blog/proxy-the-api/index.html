Put the frontend in front of the API

2026-10-13

The usual way to set up a Next.js frontend with a separate Python backend is two origins. app.example.com and api.example.com, CORS headers, a token stored somewhere in JavaScript, and a refresh flow to keep it alive.

On Ember I skipped all of that. The browser only ever talks to Next.js. Anything under /api gets proxied to FastAPI, which listens on 127.0.0.1 and isn't reachable from outside the machine.

In Next.js that's a single rewrite in next.config.ts:

const backendUrl =
  process.env.BACKEND_URL ?? `http://127.0.0.1:${process.env.BACKEND_PORT ?? 8000}`;

async rewrites() {
  return [{ source: "/api/:path*", destination: `${backendUrl}/api/:path*` }];
}

The GitHub OAuth callback goes through the same path, so the session cookie is set first-party.

What you get out of it:

  • No CORS. Same origin, so there's nothing to configure and nothing to get wrong.
  • No tokens in JavaScript. The session is an HttpOnly cookie. Scripts on the page can't read it, so an XSS bug can't steal it.
  • Smaller attack surface. The API port isn't public. The only thing on the internet is the Next.js server.
  • Simpler local dev. One URL. The same setup works on my laptop and on the server.

The cost is an extra hop for every API call, and Next.js has to be up for the API to be reachable. For a habit tracker with a handful of users that hop doesn't matter. If I needed a public API for other clients, or a mobile app talking to the backend directly, I'd think again.

At work we deal with the other end of this, where lots of different clients call the same API and the boundary has to be designed properly. For my own small projects, though, I've stopped starting with two origins. One origin is less to set up and less to secure.
