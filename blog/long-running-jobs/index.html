Things I learned building a workflow engine

2026-09-15

Between 2021 and 2023 a big chunk of my time went into a workflow engine at DronaHQ. You drag steps onto a canvas (call an API, transform data, wait for an approval, loop over rows) and it runs them on the backend, sometimes for hours. I learned more from that project than from almost anything else I've worked on. Some notes.

Assume the process will die

Anything that runs for more than a few seconds will eventually be interrupted, by a deploy, a crashed container or a node getting recycled. If a run's progress only exists in memory, a restart loses it.

So every step's state gets written down before and after it runs. When the engine starts back up it asks "what was in progress?" and picks up from there. It sounds obvious, but it changes how you design everything else.

Retries need idempotency

Once you can resume, you will run some steps twice. The engine can't tell whether a step that was mid-flight when the process died actually finished. For reads that's fine. For "charge the card" or "send the email" it isn't.

We ended up giving each step execution an ID that gets passed downstream where possible, and being explicit in the UI about which steps are safe to retry. A lot of the work was making the user aware of this without asking them to understand distributed systems.

Model it as a state machine

Early on, a run's status was a few booleans. isRunning, hasFailed, isPaused. You can guess how that went. Moving to an explicit state machine with defined transitions (queued, running, waiting, failed, completed, cancelled) removed a whole class of "how did it get into this state?" bugs. Invalid transitions just throw.

Logs are part of the product

When a ten-step workflow fails at step seven at 3am, the person debugging it is a customer, not us. The run history, with inputs and outputs for every step, turned out to be one of the most used parts of the feature. We had treated it as a debugging aid. Customers treated it as the main screen.

Keep the canvas dumb

The drag-and-drop editor only produces a definition, which is plain JSON. All the behaviour lives in the engine. That kept the editor easy to change and meant we could test the engine without touching any UI.

None of these ideas are original. You'll find the same lessons in any write-up about job queues or orchestration tools. But each one came from a real support ticket, which is probably why they stuck with me.
